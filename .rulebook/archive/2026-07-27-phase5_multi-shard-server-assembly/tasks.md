## 1. Implementation
- [x] 1.1 Provision `sharding.shards` hosts — `boot::assemble` builds N `ShardHost`s behind a `ShardCoord`, each fully independent (SHD-020): its own pager over an even split of the buffer pool, store, recovery, commit log, pipeline, checkpoint worker and replication primary, under `shard-<k>/` subdirectories. A count whose per-shard pool falls below the floor is **refused** with the arithmetic in the error. Two scope decisions recorded in SPEC-007/DEPLOYMENT.md: (a) only an **explicit** count provisions multi-shard — honouring the hardware-derived `auto` would let a core count silently flip the on-disk layout on upgrade (an implicit re-partition, SHD-003), and it broke `backup_e2e` on the 32-core dev box the moment it was allowed; (b) `shards = 1` builds no coordinator at all, so the single-shard assembly and flat data layout are byte-for-byte the pre-existing ones.
- [x] 1.2 Route connections and calls — a session resolves its affinity shard at `Authenticate` (SHD-011: identity hash for partitioned schemas, default shard otherwise), rebinds its context, and every read/write/subscription runs there; the binding is connection-lifetime and recorded in the persisted caller's `shard_id`, so the per-request HTTP transport re-resolves it identically. Reducer calls route through the coordinator (`call_idempotent`), so SHD-030 global replication and SHD-040 move detection run on the transport path. **Fixed a latent T5.4 bug this surfaced**: `ShardRouter::affinity_of` hashed raw identity bytes while row placement hashes the FluxBIN encoding, putting a caller's connection and rows on different shards for ~half of identities — every insert read as an entity move and the first assembled boot hung in the handoff storm. Nothing had caught it because nothing had ever called `affinity_of`.
- [x] 1.3 Shard-aware admin — `/metrics` emits every host's storage blocks (table rows, memstore estimate, TIER-080 pool series, TIER-061 reclaim gauges), HELP/TYPE headers once and series per shard. The transports register/deregister fan-out handles on the **session's** shard rather than the listener's, or a rebound session would never receive its shard's TxUpdates.
- [x] 1.4 Checkpointing, recovery and replication per shard — each shard recovers its own checkpoint + log on boot, runs its own checkpoint worker (archive dir and remote prefix namespaced per shard), and installs its own `ReplicationPrimary`; `ReplicaHello` routes by its `shard_id` field to that shard's primary. Node-level services (T7.2 election, CDC pumps) stay on the default shard; per-shard CDC fan-in is documented future work. Follower-side multi-shard replication (a replica dialing one client per shard) is untested — the primary side is wired; exercising N replica clients end to end belongs to a replication-focused follow-up.
- [x] 1.5 Verification — new `multi_shard_e2e` suite drives the **real boot path**: a partitioned table registered by the test binary, two identities with different affinities writing through real sessions, rows landing on exactly their shards, the per-request rebuild re-resolving the binding, the unhostable-count refusal (budget pinned — the derived budget on a large workstation genuinely hosts 4096 pools, which the first version of the test learned the hard way), and per-shard `/metrics` blocks over a live HTTP listener. `fluxum-bench soak --shards 2` observes 2 shards within their own pool capacities and PASSes. The coord-level `shard_coord`/`entity_handoff` suites keep their hand-built hosts (they test the library); the assembly path is what this suite covers.
- [x] 1.6 Soak tightened from warning to **failure** when `shards_observed < shards_requested` — a disagreement can now only mean the metrics scrape missed shards. `docs/SOAK.md` drops the "--shards does not shard" caveat, noting the remaining gap: the demo module's tables are unpartitioned, so identity affinity resolves every session to shard 0 and a sharded soak spreads sessions, not rows; partitioning a demo table is tracked in the T7.7 task.
