## 1. Implementation
- [ ] 1.1 Provision `sharding.shards` hosts: `boot.rs` builds N `ShardHost`s behind a `ShardCoord` instead of hard-coding shard 0, each with its own store, commit log, page file and checkpoint worker. A configured shard count is either honoured or refused at startup — the current silent downgrade to one shard is the outcome to eliminate.
- [ ] 1.2 Route connections and calls by partition key through the coordinator (SHD-001..004), with tables lacking `partition_by` on shard 0 (SHD-004/OQ-6). Both transports (TCP and HTTP) resolve the target host per request; a reducer touching a key owned elsewhere follows the existing handoff path rather than committing locally.
- [ ] 1.3 Make the admin surface shard-aware: `/health` and `/metrics` report every host, not just one. The TIER-080 and `fluxum_table_rows` series already carry a `shard` label but always emit 0 today — confirm each host's block is distinct, since the soak's per-shard budget assertion (TST-112) reads exactly these labels and would otherwise judge one shard N times.
- [ ] 1.4 Thread checkpointing, recovery and replication per shard, so a restart restores every host's own state and a replica follows each shard's log.
- [ ] 1.5 Verification: the `shard_coord` and `entity_handoff` suites run against the **assembled server** rather than hand-built hosts; a 2-shard end-to-end run (auth → subscribe → reducer → TxUpdate, spanning both shards) passes; and `fluxum-bench soak --shards N` reports `shards_observed == N`.
- [ ] 1.6 Tighten `fluxum-bench soak` from warning to **failing** when `shards_observed < shards_requested`, and drop the `--shards` caveat from `docs/SOAK.md`. The warning exists only because the capability was unreachable; once it is reachable, a run that did not shard is a broken run.
