- [x] 1.1 Build the soak harness: sharded + tiered deployment loaded to >= 1 billion rows with sustained writes AND live subscriptions throughout (NFR-13, TST-112) — `fluxum-bench soak` (commit d2fd1ec) loads, sustains writes + live subscriptions, and samples throughout; validated end-to-end at small scale by `tests/soak_smoke.rs` against a real release server.
- [x] 1.2 Memory-within-budget assertion for the whole soak (RSS ceiling per FR-110/TIER-004); soak report published as a release artifact — peak RSS vs `budget + max(tolerance, 10% of budget)`, plus the two witnesses TST-111 actually requires, which were missing: the SPEC-015 TIER-080 buffer-pool gauges were never wired into the server's `/metrics` (`samples()` had sat there since T2.8 labelled "ready for the T5.6 exporter"), so nothing outside the process could sample them. Now exposed with a `shard` label, scraped on the RSS cadence, and reduced to per-shard peaks against each shard's own capacity — TST-112 asks for "within budget on every shard", which one process-wide RSS figure cannot show since shards share a process. Eviction-engaged and the NFR-12 idle ceiling join the verdict, each gated by whether the profile demands it (`--profile droplet|billion`). `SoakReport` round-trips through JSON like the parity report.
- [x] 1.3 Small-droplet profile validation: 1 vCPU / 512 MB with dataset >= 10x RAM passes the full functional profile; idle baseline RSS < 100 MB (NFR-12, TST-110/TST-111, HWA-021) — `fluxum-bench droplet` implements the TST-110 requirement that was entirely absent: a constrained run's row sets compared against an unconstrained **reference run**. Every other tiering assertion is a bound; only a comparison catches a row that returns *wrong* after evict/fault-in. Multiset diff over self-identifying `u{user}-r{index}` rows, so a lost row, a corrupted one (same count!), a duplicate, and an `owner_only` leak are each distinguishable. The 10x ratio is measured from the cold tier on disk and a dataset that did not clear it is a FAIL. `.github/workflows/droplet-profile.yml` runs both halves under a `systemd-run` scope (CPUQuota=100%, MemoryMax=512M, MemorySwapMax=0) and aborts if the runner lacks cgroup v2.
- [~] 1.4 Verification (DAG exit test): soak report - memory within budget throughout; droplet suite green with one documented command — **the commands and their exit criteria exist and are documented (`docs/SOAK.md`); the launch-defining runs have not been performed.** The witnesses themselves *were* validated under real pressure (200k rows / 128 MiB budget: pool peaked at 101.8 MiB against a 102.4 MiB capacity with ~730k evictions, so `eviction_engaged` and the per-shard check were observed firing positively, not just in no-pressure runs).
