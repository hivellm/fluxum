## 1. Implementation
- [x] 1.1 Diagnose *why* reclamation lags — **the SPEC-022 RV-020 temporal window**. Instrumenting the reclaimer showed 64 versions pinned during a plain commit loop holding no snapshots, with the reclamation floor stuck far behind the newest version. The window retains the last N commits' snapshots for `AS OF`, and each retained snapshot pins its version, which pins every page that version's commit superseded. Setting `temporal_window: 0` removed the cliff entirely and dropped pool occupancy to the live set, isolating the window as the sole cause. Not cadence, and not reachability bookkeeping — the reclaimer was correct and prompt; it was being handed versions it was not allowed to free. Root of the mismatch: the window's count bound was costed for the *resident* store, where retaining a snapshot cost only the `imbl` chunks a commit touched; on the paged store it pins whole page versions, so the cost became `superseded pages per commit x window` with nothing bounding transaction size.
- [x] 1.2 Reclamation-lag observability as permanent metrics — `fluxum_reclaim_pending_pages`, `fluxum_reclaim_live_versions`, `fluxum_temporal_window_snapshots` and `fluxum_temporal_window_budget_evictions_total` ride `/metrics` beside the TIER-080 series, plus `MemStore::reclaim_pending()` in-process. A pool full of live pages and one full of version garbage waiting on a pinned snapshot look identical from `fluxum_bufferpool_bytes` alone, and they call for opposite responses.
- [x] 1.3 Fix — `temporal_window_max_bytes` (default: a quarter of the pool) enforces RV-020's "bounded by budget" half, which the implementation had never had. When it binds, the oldest snapshots go first, trading `AS OF` reach exactly as RV-021's out-of-window error already covers. TIER-061 is untouched: nothing is retired while a live version can reach it, and popped snapshots are dropped outside the history lock so reclamation I/O never runs beneath it.
- [x] 1.4 Verification — measured on a 100 000-row table (~5 MB live, 256 MiB pool): 200 rows/tx 33 058 → 50 542 rows/s, 400 → 4 561 → 53 034, 800 → 1 563 → 53 661, 2 000 → ~1 270 → 55 741, with pool occupancy falling from 153-241 MiB to 27-52 MiB. **Zero page writes and zero evictions at every transaction size**; throughput no longer depends on transaction size at all. `store_acid`, `temporal_as_of`, `txn_atomicity` and the crash suites stay green.
- [x] 1.5 Re-measured the T7.7 soak load path and recorded it in `docs/SOAK.md` — **the fix did not change it** (~3 600-4 400 rows/s, unchanged), and was not expected to once the cause was known: the soak writes one row per `add_task` reducer call, and single-row commits pin so little superseded state that the byte ceiling never binds. The 60+ hour extrapolation for 1e9 rows therefore stands. `docs/SOAK.md` and the proposal both now say so explicitly, since the proposal had claimed otherwise. Criterion baseline refresh deferred — see the note below.

## Notes / follow-ups
- **Criterion baselines are still stale.** `target/criterion/` predates the paged live store, so `cargo bench` reports a large false "regression" (+98% on `txn_commit_update_reading_1000`, +294% on the 1M case) that is really the accepted cost of paging; the absolute NFR-03 gate passes comfortably (p99 220 µs at 1M rows against 1 ms). Not refreshed here: the baselines are machine-local and untracked, so refreshing them from this workstation would encode its noise. Worth doing on a quiet, canonical machine.
- **The soak's load bottleneck is a separate problem.** One serialized commit per row, ~44 µs in-process and ~88 µs over the network, against NFR-01's 100 000 tx/s per shard. The levers are batching (needs a bulk reducer in the demo module) and sharding (`phase5_multi-shard-server-assembly`).
